# Salesforce Architecture & Refactoring Explorer - Architecture Audit & Findings

## 1. Executive Summary & Core Architectural Rules

This document outlines the architecture findings, data models, and adapter boundary recommendations for building a read-only **Salesforce Architecture & Refactoring Explorer** on top of `dependency-analyzer.cjs`.

### Architectural Directives:
1. `dependency-analyzer.cjs` is the **single source of truth** for dependency analysis, symbol registry, graph resolution, metrics, and risk calculation.
2. The Explorer **MUST NOT reimplement dependency analysis** or recalculate graph metrics, fan-in/fan-out, risk scores, or cycles.
3. The Explorer **MUST NOT depend on `orchestrator.js`**.
4. The Explorer **MUST NOT require an LLM**.
5. Analyzer behavior **MUST NOT be modified** unless explicitly required.
6. Existing functionality and CLI outputs must remain completely preserved.

---

## 2. Analysis of `dependency-analyzer.cjs` Data Models & Functions

`dependency-analyzer.cjs` is a deterministic static analysis engine scanning Salesforce metadata (`ApexClass`, `ApexTrigger`, `LWC JS/HTML`, `Visualforce`, `Flow`, `CustomObject`, `CustomField`).

### Key Internal Functions:
- `discover(sourceDir)` (line 484): Scans metadata directory structure.
- `buildRegistry(discovered)` (line 1403): Constructs the raw symbol registry.
- `enrichRegistry(registry)` (line 2945): Enriches component intelligence (methods, security signals, DML, async, test relationships).
- `buildGraph(discovered, registry, options)` (line 1501): Builds graph nodes and edges.
- `enrichGraphEvidence(graph, registry)` (line 3201): Attaches method call locations and source code evidence to edges.
- `metrics(graph)` (line 1920): Computes Fan-In, Fan-Out, Coupling, Unresolved Count, Score, and Risk classification (`HIGH`, `MEDIUM`, `LOW`).
- `stronglyConnectedComponents(graph)` (line 2006): Detects circular dependency groups using Tarjan's SCC algorithm.
- `classifyUnresolvedReference(name, type)` (lines 1483 & 3884): Classifies unresolved targets (e.g., standard platform namespaces like `System`, `Schema`, `Limits`, or missing custom symbols).
- `impactFor(targetName, graph, registry, options)` (line 2179): Computes direct and transitive dependencies/dependents and impacted tests.
- `refactorAssessment(targetName, graph, registry, options)` (line 2277): Assesses refactoring risk, breaking change risks, and mitigation strategies.
- `analyze(sourceDir, options, writeOutputs)` (line 5226): Runs repository analysis and outputs report JSON files.
- `getAnalysis(sourceDir, options)` (line 3427): In-memory getter supporting snapshot caching.

### Node Model Structure:
Nodes follow the format `<Type>:<Name>`:
```json
{
  "id": "ApexClass:AssetDashboardService",
  "name": "AssetDashboardService",
  "type": "ApexClass",
  "file": "force-app/main/default/classes/AssetDashboardService.cls"
}
```

### Edge Model Structure:
Edges capture directional relationships with source code location, method owner, and canonical resolution metadata:
```json
{
  "id": "ApexClass:Controller|ApexClass:Service|method-call|doWork|Service.doWork()",
  "from": "ApexClass:Controller",
  "to": "ApexClass:Service",
  "type": "method-call",
  "method": "doWork",
  "evidence": "Service.doWork()",
  "unresolved": false,
  "confidence": "high",
  "line": 42,
  "column": 12,
  "methodOwner": "handleRequest",
  "file": "force-app/main/default/classes/Controller.cls",
  "resolutionCategory": {
    "classification": "RESOLVED_LOCAL",
    "resolution": "EXACT",
    "confidence": "high",
    "reason": "Exact match found in symbol registry."
  },
  "canonical": {
    "source": { "type": "ApexClass", "name": "Controller", "method": "handleRequest" },
    "target": { "type": "ApexClass", "name": "Service", "method": "doWork" },
    "relationship": { "type": "method-call", "resolution": "EXACT" },
    "location": { "line": 42, "column": 12 }
  }
}
```

## 3. Existing JSON Artifacts to Consume

The read-only Explorer will consume the JSON artifacts generated by `dependency-analyzer.cjs analyze [sourceDir]`:

1. **`analyze/dependency-report.json`**:
   Main repository analysis output containing:
   - `inventory`: Total count by metadata type.
   - `nodes`: Array of all component nodes.
   - `edges`: Array of all canonical dependency edges.
   - `metrics`: Calculated Fan-In, Fan-Out, Coupling score, Risk category, and reasons per component.
   - `cycles`: Array of circular dependency node ID groups.
   - `registry`: Parsed component intelligence and metadata.

2. **`analyze/architecture-metrics.json`**:
   High-level architectural metrics summary:
   - `highestImpact`: Top components sorted by coupling/risk.
   - `highRiskCount`, `mediumRiskCount`, `lowRiskCount`: Component risk breakdown.
   - `cycleCount`: Total circular dependency groups count.

3. **`analyze/analysis-snapshot.json`**:
   Cache artifact for fast incremental analysis loading and file state tracking.

4. **`component-context/<ComponentName>/01-CONTEXT.json`** *(Optional component detail)*:
   Full component intelligence package including methods, behavior signals, security checks, and refactoring impact assessment.

## 4. Dangerous Data to NOT Recalculate in Frontend

To prevent divergence, race conditions, or performance degradation, the frontend MUST NOT recalculate:

1. **Fan-In / Fan-Out / Coupling**: Calculating these in the frontend risks divergence if filtering/view modes are applied in UI.
2. **Risk Category (`HIGH`, `MEDIUM`, `LOW`) & Risk Scores**: Risk evaluation formulas belong strictly in `dependency-analyzer.cjs`.
3. **Circular Dependency Groups**: Re-running Tarjan's SCC algorithm in JS UI is expensive and duplicates complex analyzer logic.
4. **Unresolved Reference Classification**: Standard platform namespace vs missing custom symbol classification must remain analyzer-driven.
5. **Transitive Reachability & Test Impact**: Dependency trees and affected test calculations must be loaded directly from analyzer outputs.

## 5. Recommended Explorer Data Adapter Boundary

The Explorer boundary should be a lightweight read-only data loader/adapter layer:

```
+-------------------------------------------------------------+
|              Salesforce Metadata Repository                 |
+-------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------+
|                   dependency-analyzer.cjs                    |
|  (CLI / Exported Functions: analyze, getAnalysis, impact)  |
+-------------------------------------------------------------+
                              |
                              v Output Static JSON / In-Memory Object
+-------------------------------------------------------------+
|                  Explorer Data Adapter                      |
|  - Loader for dependency-report.json & architecture-metrics |
|  - Indexer for fast frontend lookup (nodeById, edgesByNode) |
|  - Zero business logic / Zero metric recalculation           |
+-------------------------------------------------------------+
                              |
                              v Read-Only Props
+-------------------------------------------------------------+
|             Salesforce Architecture Explorer UI             |
|  - Graph / Dependency Map View                              |
|  - Component Detail / Metrics Drawer                        |
|  - Circular Dependency & Risk Highlight Panels              |
|  - Refactoring Impact & Test Matrix View                    |
+-------------------------------------------------------------+
```

### TypeScript Data Adapter Interface:

## 6. Risks & Compatibility Concerns

1. **Output Directory Resolution**: `dependency-analyzer.cjs` writes by default to `./analyze/`. The adapter should support standard defaults with configurable path overrides.
2. **UI Graph Performance**: Orgs with thousands of dependencies will produce dense edge graphs. Frontend rendering should use virtualized lists and canvas/WebGL graph viewers (e.g. React Flow, Cytoscape, or D3 canvas) rather than rendering SVG/DOM elements for all nodes/edges simultaneously.
3. **CommonJS vs ESM Interop**: `dependency-analyzer.cjs` is CommonJS. Modern frontend tooling should consume the static JSON outputs or communicate via Node API/IPC to avoid CJS bundler issues.
